Systemüberblick — Rolltor OPC UA Simulation

01 / FLOWCHART
Aktualisiert: 27.05.2026 v0.1

Das Rolltor-Projekt simuliert ein rolltor mitGUI, motorsteuerung und opc ua-kommunikation. es besteht aus drei hauptkomponenten: der ui-anwendung (rolltorapp), dem opc-ua-server und dem opc-ua-client. alle komponenten kommunizieren über asynchrone tasks.

UI
RolltorApp · customtkinter
Visuelle simulation eines rolltors mit canvas-rendering, motorsteuerung und endschalter-sensoren. position 0-100% mit trägheits-berechnung.
Server
OPC UA Server · asyncua
Stellt alle rolltor-variable über opc-ua protokoll zur verfügung: position, fehler, motor auf/ab, endschalter. schreibbare variablen für fernsteuerung.
Client
OPC UA Client · asyncua
Verbindet sich mit einem OPC UA Server, abonniert motor-up/down über data-change und schreibt position, fehler und endschalter-zustände zurück.

Was zeigt dieses Diagramm?

Das Diagramm zeigt die drei hauptkomponenten des rolltor-projekts: die UI-Anwendung (customtkinter), den opc-ua-server und den opc-ua-client. alle drei arbeiten über einen gemeinsamen zustand (var_up, var_down, pos, error) zusammen.

01
RolltorApp (oben): Die GUI-Anwendung basiert auf customtkinter und zeichnet ein rolltor mit führungsschienen, jalousielamellen und motor. sie berechnet position, geschwindigkeit und trägheit alle 20ms im async_mainloop.
02
OPC UA Server (Mitte): Wenn der Server-Modus wählt, wird ein OPC UA Server gestartet, der 6 variablen über den namespace http://th-koeln.de/ait/opcua/rolltor/ bereitstellt. Motor_Up und Motor_Down sind schreibbar — das ermöglicht fernsteuerung von aussen.

Start-Modi (unten): main.py kann in drei Modi gestartet werden: --mode server (nur server), --mode client (nur client, braucht externen server) oder --mode both (eigener server + client). config.json enthält die server-url und node-id mapping.
Analogie: Stellen sie sich eine rollobertür vor. die UI ist die taschenlampe, mit der sie das tor sehen. der server ist die türsteuerung in der garage, die jeder erreichen kann. der client ist die fernbedienung, die status abfragt und befehle sendet. config.json ist der Schlüssel, der weiss, welche adresse die türsteuerung hat.

Die RolltorApp-klasse ist das herzstück der visuellen simulation. sie basiert auf customtkinter und rendert ein rolltor mit führungsschienen, jalousie-lamellen, endschalter-leds und motor-visualisierung auf einem tk-canvas.

Was zeigt dieses Diagramm?

Die RolltorApp verwaltet den gesamten zustand des rolltors — position, geschwindigkeit, fehler und motorsteuerung. der _update_logic berechnet neue position basierend auf motor-eingabe und trägheit. der _draw_canvas zeichet das visuelles bild.

01
Hintergrundbild: Beim starten wird ein foto aus assets/images/kyrgyzstan-info.jpg geladen und auf canvas-grösse zugeschnitten. falls das laden fehlschlägt, wird ein dunkler hintergrund gerendert.
02
Steuerelemente (rechts): vier schaltflächen steuern den motor (auf/ab) und die endschalter (oben/unten). alle verwenden latching-logik — druck schaltet ein, weiterer druck schaltet aus. ein reset-knopf löscht den fehlerzustand.
03
Interlock: Auf und Ab können nicht gleichzeitig aktiv sein. wenn eine richtung gedrückt wird, wird die andere automatisch deaktiviert. das verhindert einen fehlerzustand durch gleichzeitige eingabe.
04
Trägheit: die aktuelle geschwindigkeit ändert sich schrittweise (accel=0.1) in richtung zielgeschwindigkeit (±0.3). das erzeugt eine realistische bwegung statt instantanem starten/stoppen.
Analogie: Stellen Sie sich eine büroklappe vor. wenn sie aufdrücken, fährt sie nicht sofort mit vollem tempo hoch — sie beschleunigt langsam. wenn sie loslassen, hält sie nicht sofort an, sondern kommt langsam zum stehen. genau so verhält sich das rolltor.

Motorsteuerung — Latching-Logik & Physik

03 / SEQUENCE
Aktualisiert: 27.05.2026 v0.1

die motorsteuerung basiert auf einer latching-logik: drücken einschalten, erneut drücken ausschalten. zwei BooleanVars (var_up, var_down) steuern die richtung, endschalter deaktivieren den motor automatisch.

Motorsteuerung — Ablaufdiagramm

FEHLER !!!" else error == False UI->>Logic: up && down? Logic-->>UI: Ja → trigger_error() Logic-->>UI: Nein Logic->>UI: pos >= 100.0? Logic-->>UI: Ja → var_upper_limit = true Logic->>UI: pos <= 0.0? ◈
Was zeigt dieses Diagramm?

die motorsteuerung läuft im _update_logic alle 20ms ab. sie prüft fehler, endschalter, berechnet geschwindigkeit ünderung und update die position.

01
Interlock: wenn up und down gleichzeitig true sind, wird sofort ein fehler ausgelöst. das simuliert ein kurzes schließen bei motor-relais.
02
Endschalter: bei pos >= 100.0 wird var_upper_limit auf true gesetzt. bei pos <= 0.0 wird var_lower_limit auf true gesetzt. das deaktiviert den motor automatisch und leuchtet die entsprechende LED auf dem canvas.
03
Trägheits-physik: current_speed ändert sich schrittweise um accel (0.1) pro frame. wenn auf gedrückt, steigt die geschwindigkeit auf max 0.3. wenn ab gedrückt, sinkt sie auf -0.3.
04
Overtravel Fault: die position darf 102% nicht überschreiten und -2% nicht unterschreiten. wenn doch, wird ein fehler ausgelöst — das simuliert ein mechanisches überfahren der endlagen.
Analogie: so funktioniert eine echte rollobertür. die endschalter sind physikalische schalter, die den motor abschalten, wenn das tor vollständig offen oder geschlossen ist. die überfahrtsabsicherung verhindert, dass der motor über die anhalteposition hinaus läuft — wenn doch, hört man einen knall und der antrieb schaltet ab.

Was zeigt dieses Diagramm?

der opc-ua-server erstellt einen server mit dem namespace http://th-koeln.de/ait/opcua/rolltor/ und stellt 6 variable bereit. motor_up und motor_down sind schreibbar, sodass externe systeme das tor direkt steuern können.

01
Server-Initialisierung: ein neuer asyncua Server wird erstellt und auf opc.tcp://0.0.0.0:4840/th-koeln/opcua/ gehört. der benutzerdefinierte namespace http://th-koeln.de/ait/opcua/rolltor/ wird registriert.
02
Variablen erstellen: 6 variablen werden unter dem Objekt Rolltor erstellt. Motor_Up und Motor_Down werden mit set_writable() markiert — das ist die einzige möglichkeit, das tor von aussen zu steuern.
03
Subscription: ein SubHandler abonniert data-change events auf Motor_Up und Motor_Down. wenn ein externer client den wert ändert, wird die zustandsaenderung sofort an die RolltorApp weitergeleitet.
04
Loop: alle 100ms werden die aktuellen werte der rolltorapp (pos, error, motor, limits) an die OPC-UA-variablen geschrieben. umgekehrt empfängt der SubHandler änderungen von aussen und leitet sie an die app weiter.
Analogie: stellen sie sich ein haus mit einem telefonanschuss vor. der server ist die zentralleitung, die mit allen zimmern verbunden ist. die 6 variablen sind die schalter in jedem zimmer. Motor_Up und Motor_Down haben eine klingeltaste (schreibbar), während die anderen nur anzeige-lichter (lesbar) sind.

Was zeigt dieses Diagramm?

der client verbindet sich mit einem externen opc-ua server, abonniert motor-up/down und schreibt position, fehler und endschalter-zustände zurück. bei verbindungsverlust wird automatisch neu verbunden.

01
Config laden: config.json enthält die server-url und die node-id-mapping (position, error, motor_up, motor_down, upper_limit, lower_limit). die node-ids werden aus dem json gelesen.
02
Wiederholter Connect: der client läuft in einer while-loop. bei verbindungsverlust wartet er 5 sekunden und versucht es erneut. das öffnet ein asynchrones context-manager-pattern.
03
Subscription: der client abonniert motor_up und motor_down über ein 500ms-intervall. wenn ein server diese werte ändert, wird ClientSubHandler.datachange_notification aufgerufen.
04
Writeback: alle 100ms werden die aktuellen werte des rolltors (pos, error, motor, limits) an den server zurückgeschrieben. damit steht dem server immer der aktuelle zustand zur verfügung.
Analogie: so funktioniert ein tablet, das mit einem server-sync-protokoll verbunden ist. sie tippen auf dem tablet (motor steuern), und das tablet zeigt ihnen automatisch den status aller anderen geräte an. wenn die internetverbindung abbricht, versucht das tablet automatisch, sich wieder zu verbinden.

Was zeigt diese Dokumentation?

der --mode both-modus ist der hauptmodus für lokale entwickelung. er startet einen eigenen dummy-server und verbindet sich als client damit.

01
Dummy Server: Startet einen OPC UA Server mit 6 schreibbaren Variablen. Keine Subscription, kein Writeback — er ist nur ein passive Ziel für den Client. 1-Sekunden-Loop ohne Logik.
02
Echter Server: Startet einen OPC UA Server mit 2 schreibbaren und 4 lesbaren Variablen. Er erstellt eine Subcription auf Motor_Up/Motor_Down und schreibt alle 100ms den RolltorApp-Zustand zurück.
03
Shutdown-Koordination: Das UI-Fenster registriert protocol("WM_DELETE_WINDOW", self._on_closing). Beim Schließen wird running = False gesetzt, der async_mainloop beendet sich, und main.py cancellt alle OPC UA-Tasks über die CancelledError-Exception.
04
Startpunkt: Der Einstieg erfolgt über if __name__ == "__main__": in main.py. Dort wird asyncio.run(main()) aufgerufen. _logger.info("Starting Rolltor application...") wird in die Konsole ausgegeben.
Analogie: Stellen Sie sich eine Lautsprecheranlage vor. Der Dummy-Server ist ein Geige, mit dem Sie das System testen können. Der echte Server ist die eigentliche Musikquelle. Beim Ausschalten der Anlage wird zuerst der Lautstärkeregler runtergefahren (running=False), bevor der Stecker gezogen wird (task.cancel).

Motorsteuerung — Pro-Taster-Fehlerabsicherung

03B / FLOWCHART
Aktualisiert: 27.05.2026 v0.1

jede motor-taste hat eine fehlerabschaltung (if not self.error). diese verhindert, dass der motor während eines fehlerzustandes manuell bedient werden kann — eine zusätzliche sicherheitsebene über die automatische abschaltung in _update_logic hinaus.

Pro-Taster-Fehlerabsicherung
flowchart TD A["Klick Motor AUF"] --> B{"self.error == False?"} B -- Nein --> C["Taste ignoriert
kein Zustandswechsel"] B -- Ja --> D["var_up togglen"] D --> E["Interlock: var_down = False"] E --> F["_sync_buttons()"] C --> G["Display: !!! FEHLER !!!"] style C fill:#2e2008,stroke:#854F0B,color:#e8eaf2 style G fill:#2e2008,stroke:#854F0B,color:#e8eaf2 
def toggle_motor_up(self):
    if not self.error:          # Fehlerabschaltung!
        new_state = not self.var_up.get()
        self.var_up.set(new_state)
        if new_state:
            self.var_down.set(False)  # Interlock
        self._sync_buttons()

def toggle_motor_down(self):
    if not self.error:          # Fehlerabschaltung!
        new_state = not self.var_down.get()
        self.var_down.set(new_state)
        if new_state:
            self.var_up.set(False)    # Interlock
        self._sync_buttons()
◈
Was zeigt dieses Diagramm?

jeder Motor-Taster hat eine zweifache Absicherung: die taster-eigene if-not-self.error-prüfung und die zustandsbasierte prüfung in _update_logic.

01
Taster-Ebene: Die toggle_motor_up/down-Methoden prüfen self.error. Wenn ein Fehler aktiv ist, wird die Taster-Eingabe ignoriert — kein Zustandswechsel, kein Interlock.
02
Logik-Ebene: _update_logic prüft, ob up UND down gleichzeitig aktiv sind. Wenn ja, wird trigger_error() aufgerufen — das simuliert ein kurzes Schließen bei Motor-Relais.
03
Manual-Sensor-Override: Die Endschalter-Tasten (Limit Oben/Unten) können jederzeit gedrückt werden — auch während eines Fehlers. Sie überschreiben die physikalischen Limits an jeder beliebigen Position.
Analogie: Wie bei einer echten Rolltor-Steuerung: wenn ein Fehler vorliegt (z.B. überfahrene Endlage), lassen sich die Tasten nicht mehr betätigen. Man muss zuerst den Not-Aus zurücksetzen (RESET-Taste), bevor die Motor-Tasten wieder reagieren.

06A / TABLE

async def vollzugriff_steuerung(tor: RolltorApp):
    # 1. Status auslesen
    print(f"Startposition: {tor.pos}%")

    # 2. Motor steuern
    tor.var_up.set(True)        # Schaltet Motor AUF
    while tor.pos < 30.0:
        await asyncio.sleep(0.1)
    tor.var_up.set(False)       # Stoppt bei 30%

    # 3. Sensoren manipulieren
    tor.manual_upper_pressed = True  # Täuscht Blockade vor
    print(f"Status: {tor.var_upper_limit.get()}")
    tor.manual_upper_pressed = False # Sensor wieder freigeben

    # 4. Fehler provozieren & Reset
    tor.var_up.set(True)
    tor.var_down.set(True)     # Auslösend: beides gleichzeitig
    await asyncio.sleep(0.5)
    tor.trigger_reset()        # System zurücksetzen

die vollzugriff_steuerung demonstriert, wie programmatisch auf das rolltor zugegriffen werden kann — ohne die gui. das ist nützlich fü testabfolgen, automatisierung und unit-tests.

01
Lesender Zugriff: alle zustandsvariablen (pos, error, var_upper_limit, var_lower_limit) können direkt ausgelesen werden — das ist die grundlage für testabfragen und loglegik.
02
Schreibender Zugriff: var_up und var_down können programmatisch gesetzt werden — das simuliert eine externe steuerung über OPC UA. die while-loops warten auf positionsschwellen.

04

Was zeigt dieses Diagramm?

config.json ist die einzige konfigurdatei des projekts. sie enthält die server-adresse und das mapping von python-variablennamen zu opc-ua-node-ids.

01
server_url: die standard-connection-string des opc-ua-servers. beim starten des clients wird diese url gelesen, um eine verbindung zum server aufzubauen.
02

03
client nutzt config: im run_opc_client() wird config.json geladen, die server_url wird für die verbindung verwendet und die nodes werden für die subscription und writeback.
04
error handling: wenn config.json nicht geladen werden kann, wird der fehler geloggt und die funktion kehrt frühzeitig zurück — der client wird nicht gestartet.
Analogie: config.json ist wie ein adressbuch. ohne die adresse (server_url) wissen sie nicht, wohin sie müssen. ohne die grundstücksnummern (node-ids) wissen sie nicht, wo genau sie klopfen müssen.

01
UI-Fehler: doppelt-steuerung und überfahrt führen zu einem fehlerzustand, der motor abschaltet und eine fehlermeldung anzeigt. ein manueller reset ist erforderlich — das simuliert den echten sicherheitsmechanismus einer rollobertür.
02
Netzwerkfehler: bei einem verbindungabbruch wartet der client 5 sekunden und versucht dann, sich automatisch neu zu verbinden. dieser prozess wiederholt sich so lange, bis die verbindung wiederhergestellt ist.
03
Konfigurationsfehler: wenn config.json nicht gelesen werden kann, wird der fehler geloggt und der client wird nicht gestartet. das verhindert silent failures beim programmstart.
04
Logging: alle fehler und zustandsänderungen werden über das logging-modul ausgegeben. ENABLE_LOGGING kann auf false gesetzt werden, um das logging vollständig zu deaktivieren.
Analogie: wie bei einer echten rollobertür — wenn sie das tor über das ende hinaus fahren lassen, schaltet der motor ab und es bleibt eine taste zum zurücksetzen. das ist absichtlich: sie müssen sicherstellen, dass der fehler wirklich behoben ist, bevor sie wieder starten.

Glossar — Begriffsübersicht

09 / TABLE
Aktualisiert: 27.05.2026 v0.1

wichtige begriffe und abkürzungen im zusammenhang mit diesem projekt.

OPC UA Infrastruktur
Open Platform Communications Unified Architecture. Ein industrielles Kommunikationsprotokoll fü Machine-to-Machine-Kommunikation. Verwendet ein objekt-basiertes datenmodell mit namespaces, nodes und variablen.
asyncua Bibliothek
Eine Python-Bibliothek für OPC UA Client/Server-Kommunikation mit asyncio-Unterstützung. Ermöglicht asynchrone server-erstellung, node-hierarchien, subscriptions und data-change notifications.
CustomTkinter Bibliothek
Ein Python GUI-Framework basierend auf Tkinter mit modernen designs, dark-mode support und rundete widgets. wird für die rolltor-UI verwendet.
BooleanVar Algorithmus
Ein tkinter-Variable-Typ fü boolesche werte. wird verwendet, um den zustand von motor-up, motor-down und endschaltern mit reactive updates in der UI zu verfolgen.
Subscription Infrastruktur
Ein OPC UA-Mechanismus, bei dem ein client oder server auf änderungen bestimmter variablen wartet. bei einer änderung wird ein callback aufgerufen.
Node ID Format
Die eindeutige identifizierung einer opc ua-variable. Format: ns=N;s=Name (namespace index und string identifier) oder ns=N;i=N (numeric identifier).
Latching Algorithmus
Ein steuerungsprinzip bei dem ein taster ein und aus schaltet. beim ersten druck wird das signal aktiviert, beim zweiten druck wird es deaktiviert.
Trägheit Algorithmus
Die physische eigenschaft, dass sich ein objekt nicht instantan beschleunigen kann. im rolltor-simulator wird sie durch schrittweise geschwindigkeitsänderungen simuliert.
